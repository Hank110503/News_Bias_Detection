# 新设备部署文档

## 1. 适用范围

本文档面向两种部署方式：

1. 网页版本地运行
   在浏览器中通过 `Vite dev server` 运行前端。
2. 桌面版运行
   通过 `Tauri` 作为桌面应用运行。

注意：

- 当前项目不是“纯静态网页随处上传即可访问”的结构。
- 样例图片依赖仓库内本地文件。
- 因此前端必须能访问 `war_news_bias_detection/data/...` 目录。

## 2. 迁移原则

迁移到新设备时，请迁移整个仓库：

```txt
war_news_bias_detection/
```

不要只迁移：

```txt
war_news_bias_detection/frontend/
```

必须保证这些目录的相对位置不变：

- `frontend/`
- `data/processed/imgs/war_imgs_total/`
- `data/processed/texts/articles_texts/`
- `outputs/stage2_v3/`

## 3. 新设备基础环境

推荐环境：

- `Node.js 20.x`
- `npm 10+`

最低建议：

- `Node.js 18+`

桌面版额外需要：

- `Rust`
- `cargo`
- Tauri 对应系统依赖

不建议继续使用旧机器上的 `Node 16` 方案。

## 4. 迁移后通用准备步骤

进入前端目录：

```bash
cd war_news_bias_detection/frontend
```

安装依赖：

```bash
npm install
```

重新生成前端 demo 数据：

```bash
npm run sync:data
```

为什么要重新执行：

- 当前 `eval_cases.json` 存的是“相对仓库根目录”的图片路径。
- 前端运行时会根据当前机器上的仓库根目录重新解析图片。
- 因此在新设备上应重新启动或重建前端，不要直接沿用旧机器的运行进程。

## 5. 网页版部署

### 5.1 推荐方式：本地开发服务运行

这是当前最稳定、最符合现有设计的网页版运行方式。

执行：

```bash
cd war_news_bias_detection/frontend
npm install
npm run sync:data
npm run dev
```

然后打开终端输出里的本地地址，例如：

```txt
http://127.0.0.1:1431/
```

### 5.2 为什么网页版推荐 `npm run dev`

因为样例图片不是 Web 静态资源，而是仓库内的本地文件：

```txt
data/processed/imgs/war_imgs_total/*.jpg
```

当前图片显示机制依赖：

- Vite 注入仓库根目录
- `/@fs` 读取仓库内本地文件
- `server.fs.allow` 放行仓库根目录

这些能力在 `npm run dev` 下成立。

### 5.3 网页版自检步骤

1. 确认图片目录存在：

```bash
ls war_news_bias_detection/data/processed/imgs/war_imgs_total
```

2. 确认 demo 数据已生成：

```bash
ls war_news_bias_detection/frontend/public/demo
```

3. 确认 `eval_cases.json` 中图片路径是仓库相对路径，例如：

```txt
data/processed/imgs/war_imgs_total/bethenny-frankel-getty.jpg
```

4. 打开网页后，进入“样例库”，检查样例图是否出现。

### 5.4 网页版常见问题

#### 问题 1：图片不显示，但 JSON 路径看起来正常

最常见原因：

- 没有用新的 dev server 重新启动项目
- 还在访问旧端口上的老进程
- 图片文件实际不存在

处理方式：

```bash
npm run sync:data
npm run dev
```

#### 问题 2：看到 `403 Restricted`

原因：

- Vite dev server 不允许访问 `frontend/` 目录外的文件

当前仓库已经在 `vite.config.ts` 中处理了这个问题。
如果以后重新改配置，记得保留：

- `server.fs.allow`

#### 问题 3：`npm run build` 成功，但静态预览看不到本地图像

这是当前设计的正常结果。

原因：

- 纯静态网页没有权限访问仓库里的本地磁盘图片
- 浏览器生产环境也不能像 dev server 一样通过 `/@fs` 读取本地文件

结论：

- 当前项目支持“本地网页运行”
- 不支持“纯静态网页 + 本地仓库图片”这一组合

如果未来要支持纯静态网页，有两种方向：

1. 在构建时把图片复制进前端静态目录
2. 增加后端/本地静态文件服务

## 6. 桌面版部署

### 6.1 桌面版额外环境

除 Node/npm 外，还需要：

- `Rust`
- `cargo`
- Tauri CLI 可用环境

当前项目依赖：

- `@tauri-apps/cli`
- `@tauri-apps/api`

### 6.2 桌面版开发运行

执行：

```bash
cd war_news_bias_detection/frontend
npm install
npm run sync:data
npm run tauri:dev
```

Tauri 会先调用：

- `npm run dev`

再把前端嵌入桌面壳。

### 6.3 桌面版构建

执行：

```bash
cd war_news_bias_detection/frontend
npm install
npm run sync:data
npm run tauri:build
```

Tauri 配置见：

- [src-tauri/tauri.conf.json](./src-tauri/tauri.conf.json)

它会先调用：

- `npm run build`

再打桌面包。

### 6.4 桌面版图片机制

桌面版不是通过 `/@fs` 读图片，而是：

1. 前端拿到仓库相对路径，例如：
   `data/processed/imgs/war_imgs_total/xxx.jpg`
2. 前端根据当前仓库根目录拼出本地绝对路径
3. 再通过 `convertFileSrc(...)` 生成桌面 WebView 可访问的资源 URL

因此桌面版可迁移的前提同样是：

- 整个仓库一起迁移
- `frontend` 与 `data` 的相对位置不变

### 6.5 桌面版当前限制

当前 Tauri Rust 侧已经包含两个命令：

- `ping_bridge`
- `run_local_analysis`

这意味着目前桌面版已经能做的是：

- 作为本地 UI 壳运行
- 展示样例数据和图片
- 调用 Rust 本地桥执行真实 Python 推理
- 处理两类图片输入：
  - 仓库内或本机上的图片路径
  - 前端上传图片，Rust 会先写入临时文件再调用 Python

当前真实推理的调用链为：

1. 前端分析页优先调用 Tauri 命令 `run_local_analysis`
2. Rust 在仓库根目录执行 `infer.py --stage full`
3. 默认 adapter 为 `outputs/stage2_v3/final_adapter`
4. Python 路径解析顺序为：
   - 环境变量 `WAR_NEWS_BIAS_PYTHON`
   - `/root/miniconda3/envs/news_bias_312/bin/python`
   - `PATH` 中的 `python`

目前还没有完成的是：

- token 级流式输出
- 更完整的 Rust 侧状态桥接与任务管理
- 完全脱离仓库目录结构的独立交付

### 7.1 只需要网页版

```bash
cd war_news_bias_detection/frontend

npm run dev
```

### 7.2 需要桌面版

```bash
npm run tauri:build
```

## 8. 迁移完成后的验收清单

### 8.1 通用检查

- `frontend/node_modules` 已重新安装
- `public/demo/eval_cases.json` 已重新生成
- `data/processed/imgs/war_imgs_total/` 存在
- `outputs/stage2_v3/` 存在

### 8.2 网页版检查

- `npm run dev` 正常启动
- 首页正常打开
- “样例库”页能看到图片
- “分析台”加载样例时能看到图像预览

### 8.3 桌面版检查

- `npm run tauri:dev` 正常启动
- 应用窗口打开正常
- 样例图可以显示
- 页面路由切换正常

## 9. 未来如果要支持真正的“纯部署”

如果目标是：

- 不依赖仓库原始目录
- 不依赖本地磁盘相对路径
- 打包后直接交付给他人运行

那当前方案还不够。

建议改造方向：

1. 在构建期把样例图片复制进前端资源目录
2. 或在 Tauri/Rust 侧增加更完整的资源管理逻辑
3. 或把图片访问改成后端服务

当前这套方案的目标不是“完全脱离仓库运行”，而是：

- 迁移整个仓库到新机器后，仍能继续运行
